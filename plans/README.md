# Implementation Plans

Generated by the improve skill on 2026-08-29, against commit `aaf0aed`.

Every plan is self-contained: an executor with no knowledge of this repo or the
audit that produced these should be able to run one with only the plan file and
a checkout. Read the plan fully before starting, honour its STOP conditions,
and update your row below when done.

**Verification is the same everywhere**: `python tests/run_suite.py -j 4` must
end `OK` with 0 failures. A repository hook blocks raw `python -m unittest` —
always go through `tests/run_suite.py`.

## Where these came from

An audit of the tree at `aaf0aed`, weighted toward the five features that
shipped in one week (picture filters, quick outputs, compositing, audio volume,
raw ffmpeg options). Two read-only auditors swept nine categories; every
finding below was then re-verified against the source by hand, and several were
downgraded or rejected in that pass.

The pattern the audit found is worth stating once, because seven of these ten
plans are instances of it: **the builders are heavily tested and the dispatch
layer is not.** Argv assertions call a builder directly, so a feature can be
asked for, answered, recorded — and never reach the command. Two defects
shipped that way this week. Plan 008 is the structural answer; the rest are the
instances.

## Findings considered and rejected

- **A two-pass passlog glob breaking on `[`/`]` in filenames** — reported by an
  auditor; I could not find the glob it cites anywhere in the tree. Rejected as
  unsupported. If a real `glob` over passlog files turns up later, re-open it.
- **A full `ruff` or `mypy` configuration** — not worth doing. The architecture
  is built on `from x import *` across **90 files** carrying 2667 paired
  `# noqa: F401,F403` markers, and pyflakes downgrades undefined-name detection
  to F405 in any module with a star import — so the one check that would
  genuinely pay is neutered by the very pattern in play. mypy over 120 stdlib
  modules using `dict[str, Any]` answer bags would produce thousands of findings
  and change nothing about correctness. The 1983-test suite, **roughly 400** of
  them driving real ffmpeg, is a stronger signal than either tool would add. Plan 007 takes the narrow version instead: one unused-import
  assert inside the existing AST-walking test.
- **Renaming the `support/ext00..ext12` tier modules** — the names carry no
  meaning and `run_mux_cleanup_mode`, a whole main-menu mode, lives in
  `ext00b.py` with nothing in the name to say so. But renaming touches every
  star-import prelude in the package and the import-topology tests. Not worth
  the blast radius. A documentation table in `docs/architecture.md` would get
  most of the value; recorded here rather than planned, since it is a docs task
  nobody is blocked on.
- **Splitting the join half of `wizard_build_b.py`** (~828 lines) — rejected
  inside plan 010, but NOT for the reason first given. I claimed its functions
  were densely coupled; measured, the join half references **zero** names
  outside itself and only one of its names is used elsewhere, which makes it a
  *cleaner* seam than the one plan 010 actually takes. The real blocker is
  `tests/test_speed_frame_retention.py`, which requires any file containing
  `build_video_speed_filter(` to also contain `VIDEO_SPEED_OUTPUT_TIMING_ARGS`;
  splitting the join half leaves `wizard_build_b.py` holding the filter without
  the option. Plan 010 records the numbers so this is not re-litigated on the
  wrong grounds.
- **Ambient site-package lag** (click, cryptography, pydantic_core, pyee) —
  none of these are project dependencies. Not a finding.
- **CI being red** — GitHub Actions has never started on this repository. The
  check-run annotation is an account billing / spending-limit block, external to
  the code, and no commit can clear it. Not a repo defect and not plannable
  here.

## Found while EXECUTING, and bigger than the plan that found it

**`build_join_encode_command` never calls `build_cpu_video_filter`.** Measured
independently after plan 006's executor hit it: the only filters that builder
constructs are `build_video_speed_filter`, `build_encode_audio_speed_filter`
and its own `scale=`/`fps=` normalisation. So orientation, colour, denoise,
sharpen and fade are DROPPED on every joined job — before stage ownership is
consulted at all. No amount of `STAGE_TRANSFORMATIONS` work fixes it; it is a
builder gap. `raw_ffmpeg_args` likewise has no consumer in the three main
builders.

Not planned yet, deliberately: the follow-up should be written against the
executor's measurements rather than inference. Plan 006's four
`expectedFailure` tests are the standing record that the defect exists, and
they will go red on their own the moment it is fixed.

## Found while writing the plans, not in the original audit

Writing a plan means opening every line it cites, and that pass turned up four
things the audit had not:

- **The audio-reverse join applies the geometry twice** — now plan 011. Stage 1
  correctly owns `GEOMETRY_TRANSFORMATIONS`; stage 4 rebuilds from the original
  `answers` with three keys cleared by hand and no `stage_answers()` call, and
  `_single_input_answers` clears nothing. A Join + audio reverse + crop job
  crops twice, silently. This is the exact defect class the ownership schema was
  built to prevent, on a path that never adopted it.
- **The boomerang's backward half re-applies the picture filters** — measured:
  `transpose`, `hqdn3d`, `fade=t=in`, `volume` and the video bitrate all land a
  second time on the half it reads back. Plan 006 fixes it for free by putting
  the new answer keys in the schema, since the boomerang already routes through
  `stage_answers`.
- **A staged reverse DROPS compositing rather than repeating it.** Every stage
  rebuilds through `build_ffmpeg_command`, which has no composite shape at all,
  so an overlay on a reversed job vanishes. Not planned — it needs a decision
  (refuse the combination, or teach the pipeline to composite) rather than a
  fix, and refusing is probably right.
- **`run_audio_cut_mode` is unreachable.** `ffmwiz/modes_transform.py:146`
  defines it and its `__all__` exports it, but `run_one_job` never dispatches to
  it. Testing it would pin dead code. Delete-or-wire is a separate decision;
  recorded here so nobody writes a test for it first.

- **A whole suite is ungated.** `tests/test_speed_frame_retention.py:44`
  defines `requires_ffmpeg` and never applies it to anything. Without ffmpeg on
  PATH that suite ERRORS rather than skipping — measured: the full run without
  ffmpeg ends `FAILED (failures=0, errors=2)`. Folded into plan 007, because
  the README sentence that plan rewrites is otherwise unwriteable.

Two smaller corrections to the audit's own claims, both verified: a fade repeats
per SEGMENT of a segmented reverse (segments are not stages — a crop per segment
is correct, a time-anchored filter is not), and the "two-pass passlog glob"
finding does not exist in the tree at all.

And one correction to my own: I first put the ffmpeg-gated test count at ~323
from a static scan. Counting it empirically — running the suite twice, once with
ffmpeg on PATH and once without — gives **411 skip lines, 408 of them naming
ffmpeg or ffprobe**. A static AST count misses `setUpClass` guards that raise
`SkipTest`, so the empirical number is the one to trust and the one plan 007
teaches the executor to re-derive.

## Direction findings (options for the maintainer, not defects)

Neither is planned. Both are grounded in code that already exists, and both
become worth doing only after plan 004 lands — until the config keys are
actually read, they lead to an empty room.

- **A CLI front door.** `main()` in `FFmWiz.py:592` discards every unrecognised
  argument with a note, while `run_one_job(base_answers, config_path)` already
  accepts a config path from the interactive path. `ffmwiz video.mkv` and
  `ffmwiz --config gif-preset.env` are one flag away from working, and would
  make the tool scriptable and batchable without touching the wizard.
- **"Save this job as a config."** The wizard asks 30+ questions, Mode 2 reads
  a config, and `CONFIG_TEMPLATE` is machinery for generating one — but there
  is no path from "the answers you just gave" to "a file you can reuse". The
  asymmetry is one-directional and the pieces are all present.
